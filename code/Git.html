1.1 What is Version Control?

Version Control is a system that records and manages changes made to files over time. It allows developers to keep track of every modification made to a project, view previous versions, compare changes, restore older versions when needed, and collaborate with other developers without losing work.

In software development, source code changes continuously. New features are added, bugs are fixed, and existing functionality is modified. Without a proper system to manage these changes, developers would have no reliable way to know what changed, who changed it, when it was changed, or how to return to an earlier working version if something goes wrong. Version Control solves this problem.

Understanding the Problem Before Version Control Existed

To understand why Version Control exists, imagine you are developing a PHP project. Initially, your project contains only a single file. 


index.php

<?php

echo "Hello World";

On the next day, you improve the project by adding a login page. 


index.php
login.php

A few days later, you modify multiple files, add new functionality, and fix several bugs. After making dozens of changes, the application suddenly stops working.

At this point, several important questions arise:

  • Which file caused the problem?
  • What exactly changed?
  • Who made the change?
  • When was the change made?
  • Can the project be restored to yesterday's working version?

Without Version Control, answering these questions becomes extremely difficult.

How Developers Managed Projects Before Version Control

Before Version Control Systems became popular, developers usually created multiple copies of the same project. 


Project/
Project_New/
Project_Final/
Project_Final2/
Project_Final_Final/
Project_Final_Latest/
Project_Final_Latest2/

Although this method keeps previous versions, it introduces several serious problems.

  • Huge waste of storage space.
  • Difficult to identify the latest version.
  • Impossible to know what changed between two folders.
  • No information about who modified the files.
  • Very difficult for multiple developers to work together.

Version Control was invented to eliminate these problems.

Definition of Version Control

A Version Control System (VCS) is software that stores the complete history of changes made to a collection of files. Instead of manually creating multiple copies of a project, the Version Control System records every meaningful change and allows developers to return to any previous state whenever necessary.

What Does Version Control Store?

A Version Control System records much more than just the latest copy of a file. It maintains information such as:

  • The complete history of changes.
  • Previous versions of files.
  • The developer who made each change.
  • The date and time of every change.
  • A description explaining why the change was made.
  • The ability to restore any previous version.

Real-World Example

Imagine a team of three developers working on the same banking application.

Developer Task
Aathi Develops the Login Module.
Rahul Develops the Payment Module.
Priya Develops the Dashboard.

If all three developers manually edit the same project files and exchange ZIP files through email or messaging applications, many problems occur:

  • Someone's work may be overwritten.
  • Developers may accidentally use outdated files.
  • There is no reliable history of modifications.
  • Recovering deleted code becomes difficult.

A Version Control System coordinates these changes and maintains a reliable history of the entire project.

Advantages of Version Control

  • Maintains complete project history.
  • Allows recovery of previous versions.
  • Supports collaboration among multiple developers.
  • Tracks who changed each file.
  • Tracks when every change was made.
  • Helps identify bugs by comparing different versions.
  • Provides a safer development workflow.
  • Supports experimentation without permanently damaging the project.

Disadvantages

Version Control Systems themselves have very few disadvantages, but they require developers to learn proper workflows and discipline. Poor commit messages, infrequent commits, or incorrect usage can reduce their effectiveness.

Common Misconceptions

  • Version Control is not the same as Git.
  • Version Control is not the same as GitHub.
  • Saving a file is not the same as creating a version.
  • Version Control does not automatically save every keystroke.

Best Practices

  • Use Version Control from the beginning of every project.
  • Create meaningful versions instead of saving random copies of folders.
  • Keep the project history organized.
  • Treat Version Control as part of the development process, not as a backup tool.

Version Control is a system that records the history of changes made to a project. Git is one implementation of a Version Control System, which will be introduced in the next section.

Why Git Was Created

Git was created in 2005 by Linus Torvalds, the creator of the Linux kernel.

At that time, thousands of developers were working on the Linux kernel. Existing Version Control Systems were either slow, expensive, or unsuitable for managing such a large project.

Linus Torvalds designed Git with the following goals:

  • High performance.
  • Fast operations.
  • Support for thousands of developers.
  • Reliable version history.
  • Data integrity.
  • Offline development.

What is GitHub?

GitHub is a cloud-based hosting platform for Git repositories. It stores Git repositories online, allowing developers to share code, collaborate, review changes, and back up projects.

Git works perfectly without GitHub. GitHub simply provides an online location where Git repositories can be stored and shared.

Centralized VCS vs Distributed VCS

Before Git became popular, most Version Control Systems followed a Centralized architecture. Understanding this difference explains why Git works the way it does.

In a Centralized Version Control System, there is a single central server that stores the complete repository. Every developer connects to that server to obtain the latest files and submit changes.

    │         │         │

Advantages

  • Simple architecture.
  • Centralized administration.
  • Easy permission management.

Disadvantages

  • Single point of failure.
  • Internet connection usually required.
  • Limited offline work.
  • If the server fails, development is disrupted.

Examples

  • CVS
  • Subversion (SVN)

In a Distributed Version Control System, every developer has a complete copy of the repository, including its entire history. Development can continue even without a network connection.

  • No single point of failure.
  • Every developer has a complete backup.
  • Very fast local operations.
  • Better support for branching and merging.

Disadvantages

  • More concepts for beginners to learn.
  • Requires synchronization with remote repositories when collaborating.

Examples

  • Git
  • Mercurial

2. Installation

Before using Git, it must be installed on your computer. Installing Git provides the Git executable, which allows you to create repositories, track changes, manage versions, and collaborate with other developers.

Once Git is installed, it can be used completely offline. An internet connection is only required when communicating with a remote repository such as GitHub, GitLab, or Bitbucket.

Why Do We Need to Install Git?

Git is software, just like a compiler, a database server, or a web browser. Until it is installed, the operating system does not know how to execute Git commands.

When Git is installed:

  • The Git command-line tool becomes available.
  • The Git executable is added to your system.
  • You can initialize repositories.
  • You can create commits.
  • You can manage project history.
  • You can connect to remote repositories later.

Most Linux distributions provide Git through their package manager.

During installation, the package manager downloads Git and installs its executable into the system so that it can be accessed from the terminal.

After installation, it is good practice to verify that Git is installed correctly. 


git --version

Example: 


git version 2.25.1

If the version number is displayed, Git has been successfully installed and is available in your system's PATH.

How Does git --version Work Internally?

When you execute the command: 


git --version

The operating system performs the following steps:

  1. Searches for the Git executable in the directories listed in the PATH environment variable.
  2. Launches the Git executable.
  3. Git recognizes the --version option.
  4. Git reads its version information.
  5. The version number is printed to the terminal.

Configuring Git

Before creating commits, Git needs to know who is making those commits.

Every commit stores information about its author. This information is called the commit metadata.

Each commit records:

  • Author Name
  • Author Email
  • Date and Time
  • Commit Message
  • Unique Commit ID (Hash)

Why Configure Username and Email?

Git uses the configured username and email to identify the author of every commit. These values become part of the project's history.

They are not used for logging into GitHub.

This is one of the most common misconceptions among beginners.

Configure Username


git config --global user.name "Aathi"

Replace Aathi with your preferred display name.

Configure Email


git config --global user.email "your@email.com"

Replace the email address with your own email.

What Does --global Mean?

Git stores configuration at different levels.

Level Description
System Applies to every user on the computer.
Global Applies only to the current user.
Local Applies only to one repository.

The --global option stores the configuration for your user account. Every new repository you create will use these values unless overridden locally.

View Current Configuration

Display all configured Git settings: 


git config --list

Example output: 


user.name=Aathi
user.email=your@email.com

View Only Username


git config --global user.name

View Only Email


git config --global user.email

Where Does Git Store the Configuration?

When using the --global option, Git stores the configuration in a file located in the current user's home directory.

Linux: 


~/.gitconfig

Windows: 


C:\Users\Username\.gitconfig

Git reads this configuration whenever a Git command is executed.

Best Practices

  • Verify the installation immediately after installing Git.
  • Configure your username and email before making your first commit.
  • Use your real name in professional environments.
  • Use a valid email address if you plan to use GitHub.
  • Do not use sudo for normal Git commands.

Common Mistakes

  • Assuming Git and GitHub accounts are the same.
  • Forgetting to configure username and email.
  • Using sudo unnecessarily for everyday Git commands.
  • Thinking the configured email is used as a GitHub login credential.

3. Repository

Before learning Git commands such as git init, git add, or git commit, it is important to understand one of the most fundamental concepts in Git: the Repository.

Every Git operation is performed inside a repository. Whether you are creating a new project, tracking changes, restoring old versions, or collaborating with other developers, everything revolves around the repository.

What is a Repository?

A Repository (often shortened to Repo) is a storage location that contains a project's files along with the complete history of all changes made to those files.

A repository is much more than a normal folder. In addition to the project's source code, it stores information such as:

  • Every committed version of the project.
  • The complete history of changes.
  • Branch information.
  • Tags.
  • Commit messages.
  • Author information.
  • Merge history.
  • Configuration specific to the repository.

In simple terms, a repository is a project folder that Git is capable of managing and tracking.

Why Do We Need a Repository?

Imagine you have a normal project folder. 


Calculator/
├── index.php
├── login.php
└── database.php

This folder simply stores files. It has no knowledge of:

  • Who modified a file.
  • When a file was modified.
  • Why it was modified.
  • How to restore an earlier version.

After converting it into a Git repository, Git starts maintaining the history of the project. 


Calculator/
├── .git/
├── index.php
├── login.php
└── database.php

The addition of the .git directory transforms an ordinary folder into a Git repository.

Types of Git Repositories

Git repositories are generally categorized into two types:

  1. Local Repository
  2. Remote Repository

Local Repository

A Local Repository is a repository stored on your own computer. It contains the project files as well as the complete Git history.

When you execute: 


git init

Git creates a new local repository by adding a hidden directory named .git inside the project.

Example: 


StudentManagement/

├── .git/
├── app.php
├── index.php
└── database.php

Characteristics of a Local Repository

  • Exists only on your computer.
  • Works without an internet connection.
  • Stores the complete commit history.
  • Allows commits, branches, merges, and restores.
  • Does not require GitHub.

Remote Repository

A Remote Repository is a copy of a Git repository stored on another computer or server.

Common hosting services include:

  • GitHub
  • GitLab
  • Bitbucket
  • Azure DevOps
  • Private company Git servers

The purpose of a remote repository is to:

  • Share code with other developers.
  • Create project backups.
  • Enable team collaboration.
  • Review code changes.
  • Synchronize work between multiple computers.

The .git folder is the heart of every Git repository.

It is automatically created when the following command is executed:

Why is the .git Folder Hidden?

On Linux and macOS, any file or directory whose name begins with a dot (.) is hidden by default. This prevents users from accidentally modifying or deleting Git's internal data.

You can view hidden files using: 


ls -la

What is Stored Inside the .git Folder?

The .git directory stores all Git-related information. It does not contain your source code itself; instead, it stores the metadata and history required to manage your project.

A typical .git directory looks similar to: 


.git/

├── config
├── description
├── hooks/
├── index
├── info/
├── logs/

How Does Git Recognize a Repository?

Whenever you execute a Git command such as: 


git status

Git first searches the current directory for a .git folder. If it cannot find one, it searches the parent directories.

If no .git directory exists, Git displays an error similar to: 


fatal: not a git repository (or any of the parent directories): .git

This is because Git only operates inside a valid repository.

4.1 Working Directory

The Working Directory is one of the most fundamental concepts in Git. Every Git operation begins here. Before understanding commands such as git add, git commit, or git restore, it is essential to understand what the Working Directory is and how Git uses it.

Many beginners think that Git automatically tracks every change they make to a file. This is not true. Git separates your project into different areas, and the Working Directory is only the first of those areas.

What is the Working Directory?

The Working Directory is the actual project folder on your computer where you create, edit, delete, rename, and organize files. It is the directory that you open in your code editor (such as Visual Studio Code) and where you perform your day-to-day development work.

In simple words, the Working Directory is the place where you actively work on your project.

For example: 


StudentManagement/

├── .git/
├── index.php
├── login.php
├── dashboard.php
└── config.php

Everything except the .git folder belongs to your Working Directory.

Why Does Git Need a Working Directory?

Imagine Git immediately recorded every character you typed.

While writing a function, you may:

  • Type incomplete code.
  • Introduce syntax errors.
  • Delete code temporarily.
  • Experiment with different solutions.

These temporary changes should not become permanent versions of your project.

Therefore, Git allows you to freely modify files inside the Working Directory without immediately recording them into the project's history.

How the Working Directory Works

Suppose your project initially contains the following file: 


index.php

<?php

echo "Hello";

You now edit the file: 


index.php

<?php

echo "Hello World";

After pressing Ctrl + S, only the file stored in the Working Directory has changed.

Git has noticed that the file is different from the last committed version, but it has not recorded the change into the repository.

Saving a File vs Creating a Git Version

One of the biggest misconceptions among beginners is believing that saving a file automatically creates a Git version.

Saving a File Git Commit
Updates the file on your computer. Creates a permanent version in Git history.
Performed by the editor. Performed by Git.
Can happen many times. Should represent a meaningful change.
Does not change Git history. Updates the repository history.

Therefore, pressing Ctrl + S only saves the file. Git history remains unchanged until you explicitly create a commit.

What Happens Internally?

Consider the following sequence:

  1. You open a file.
  2. You modify its contents.
  3. You save the file.

Internally, the following occurs:

  • Your operating system writes the updated file to disk.
  • The file inside the Working Directory is replaced with the new contents.
  • The previous committed version stored inside Git remains unchanged.
  • Git detects that the file differs from the last committed version.
  • The change stays only in the Working Directory until you stage it.

Working Directory Example

Suppose the last committed version contains: 


<?php

echo "Welcome";

You modify the file: 


<?php

echo "Welcome to Git";

At this moment:

  • Your Working Directory contains "Welcome to Git".
  • Your Local Repository still contains "Welcome".
  • No new Git version has been created.

Working Directory in Git Architecture

The Working Directory is the first stage in Git's workflow. 


                 You Edit Files
                      │
                      ▼
             Working Directory
                      │
             (git add later)
                      ▼
               Staging Area
                      │
             (git commit later)
                      ▼
             Local Repository

Every modification starts inside the Working Directory.

What Kind of Operations Occur in the Working Directory?

  • Create new files.
  • Edit existing files.
  • Delete files.
  • Rename files.
  • Create folders.
  • Move files.
  • Refactor project structure.

Git allows all of these operations without immediately recording them in the repository.

Relationship with git status

Git continuously compares the Working Directory with the latest committed version.

If differences are found, running: 


git status

displays information such as: 


modified: index.php

Untracked files:
    login.php

This means the Working Directory contains changes that have not yet been staged or committed.

Advantages of the Working Directory

  • Allows experimentation without affecting Git history.
  • Lets developers test ideas before creating commits.
  • Supports frequent editing without generating unnecessary versions.
  • Provides complete freedom while developing.

Common Mistakes

  • Thinking saving a file automatically creates a commit.
  • Believing Git stores every keystroke.
  • Confusing the Working Directory with the Local Repository.
  • Assuming modified files are already part of Git history.

Best Practices

  • Use the Working Directory for active development only.
  • Review your changes before staging them.
  • Do not assume saved files are backed up by Git.
  • Run git status frequently to understand the current state of your Working Directory.

Understanding the Working Directory is essential because it is the starting point of every Git workflow.

4.2.1 Staging Area (Index) - Introduction

The Staging Area is one of the most unique and important concepts in Git. It is also one of the most confusing concepts for beginners because many other Version Control Systems do not have an intermediate stage before creating a version.

To understand Git properly, you must understand why the Staging Area exists. Once you understand this concept, commands such as git add, git commit, git reset, and git restore will become much easier.

What is the Staging Area?

The Staging Area (also called the Index) is a temporary area where Git stores the changes that you have selected to include in the next commit.

It acts as a bridge between the Working Directory and the Local Repository.

Instead of committing every modified file immediately, Git first asks you to decide which changes should become part of the next version.

Definition

The Staging Area is a temporary storage area maintained by Git that contains a snapshot of all the files that will be included in the next commit.

Why Does Git Need a Staging Area?

This is the most important question.

Imagine you worked on a project for an entire day. 


Project/

├── login.php
├── payment.php
├── dashboard.php
├── config.php
└── style.css

During the day you:

  • Finished the login feature.
  • Started working on the payment feature.
  • Accidentally modified the configuration file.
  • Experimented with some CSS changes.

At the end of the day, only the login feature is complete.

The payment feature is only half finished.

The CSS changes are only experiments.

The configuration file should never be committed.

If Git directly committed everything from the Working Directory, your project history would contain:

  • Finished code.
  • Incomplete code.
  • Experimental code.
  • Accidental modifications.

That would create poor quality commits.

The Solution

Git introduces the Staging Area so that developers can carefully choose what should be included in the next commit.

Instead of saying:

Commit everything.

Git asks:

Which changes do you want to include in the next version?

Only those selected changes are placed into the Staging Area.

Real World Example

Imagine you are writing an assignment.

Your notebook represents the Working Directory.

Before submitting the assignment, you copy only the final answers onto a clean sheet.

That clean sheet represents the Staging Area.

Finally, you submit the assignment.

Submission represents the Git Commit. 


Notebook

↓

Select Final Answers

↓

Clean Sheet

↓

4.3.1 Local Repository - Introduction

In the previous sections, we learned about the Working Directory and the Staging Area (Index). We now know that files are first modified in the Working Directory and then selected for the next commit by placing them into the Staging Area.

However, one important question still remains:

Where does Git permanently save our project's history?

The answer is the Local Repository.

What is a Local Repository?

A Local Repository is the database maintained by Git on your own computer. It stores the complete history of your project, including every commit, commit message, branch, tag, and other information required to reconstruct any previous version of the project.

Unlike the Working Directory, which contains the files you are actively editing, the Local Repository stores only the committed versions of your project.

Simple Definition

A Local Repository is Git's permanent storage area on your computer where all committed versions of a project are stored.

Why Do We Need a Local Repository?

Imagine you are developing a web application.

During development you may:

  • Add a new feature.
  • Fix bugs.
  • Accidentally delete important code.
  • Introduce new bugs.
  • Experiment with different implementations.

Without a Local Repository, every new change would overwrite the previous version forever.

There would be no reliable way to return to an earlier working version of the project.

The Local Repository solves this problem by keeping a permanent history of your commits.

Where is the Local Repository Stored?

When a Git repository is initialized using: 


git init

Git creates a hidden directory named .git. 


StudentManagement/

├── .git/
│
├── login.php
├── dashboard.php
└── index.php

The .git directory contains the Local Repository.

Everything required to rebuild the project's history is stored inside this directory.

If the .git directory is deleted, Git no longer recognizes the project as a Git repository, and the commit history is lost (unless another copy exists).

What Does the Local Repository Store?

The Local Repository stores much more than your source code.

  • Committed project versions.
  • Commit messages.
  • Commit identifiers (Hashes).
  • Branch information.
  • Tags.
  • Repository configuration.
  • References to previous commits.

This information allows Git to reconstruct the complete history of the project at any point in time.

9. Undoing Changes

Git provides several commands to undo changes depending on where the changes are located. You can discard changes in the Working Directory, unstage files from the Staging Area, or move commits in the Local Repository.

Choosing the Correct Command

Situation Command
Discard changes in Working Directory git restore
Unstage a staged file git restore --staged
Restore a file (older Git versions) git checkout -- <file>
Move HEAD to another commit git reset

9.1 git restore

What is git restore?

git restore restores files to their last committed state. It is mainly used to discard unwanted changes in the Working Directory or remove files from the Staging Area.

Syntax


git restore <file_name>

Example


echo "Testing" >> hello.txt

git status

git restore hello.txt

The changes made after the last commit are discarded, and the file returns to its previously committed version.

Restore a Staged File


git restore --staged hello.txt

This removes the file from the Staging Area but keeps the changes in the Working Directory.

9.2 git checkout (File Restore)

Syntax


git checkout -- <file_name>

Example

This restores hello.txt to the version stored in the latest commit, discarding local modifications.

Modern Equivalent


git restore hello.txt

9.3 git reset

What is git reset?

git reset moves the current branch (HEAD) to another commit. It can also remove files from the Staging Area and, depending on the option used, discard changes in the Working Directory.

Syntax


git reset [OPTION] <commit>

Command Effect

git reset --hard HEAD~1 Removes the last commit and permanently deletes all changes.

Examples

Unstage a File


git reset hello.txt

Removes the file from the Staging Area while keeping the changes in the Working Directory.

Undo the Last Commit


git reset --soft HEAD~1

Delete the Last Commit Completely


git reset --hard HEAD~1

12. Merge (Part 1)

Branches allow developers to work independently. After completing the work on a branch, the changes must be combined with another branch. This process is called merging.

12.1 What is Merge?

A merge combines the changes from one branch into another. Git preserves the commit history while bringing together the work from different branches.

Merging is commonly performed after a feature has been completed and tested.

Basic Merge Command

12.2 Fast-Forward Merge

What is a Fast-Forward Merge?

A Fast-Forward Merge occurs when the target branch has not changed since the new branch was created. Git simply moves the branch pointer forward without creating a new merge commit.

Before Merge

12. Merge (Part 2)

12.4 Merge Conflict

What is a Merge Conflict?

A Merge Conflict occurs when Git is unable to determine which changes should be kept while merging two branches.

This usually happens when the same part of the same file has been modified differently in two branches.

Example

Suppose the file login.php contains:


echo "Login";

main branch:


echo "User Login";

login-feature branch:

Both branches changed the same line differently. When Git tries to merge them, it cannot decide which version should be kept.

Merge Attempt


git switch main

git merge login-feature

Example Output:


Auto-merging login.php

CONFLICT (content): Merge conflict in login.php

Automatic merge failed; fix conflicts and then commit the result.

Conflict Markers

Git places special markers inside the file to indicate the conflicting changes. 


<<<<<<< HEAD
echo "User Login";
=======
echo "Customer Login";
>>>>>>> login-feature
Marker Meaning
<<<<<<< HEAD Current branch version.
======= Separates the two versions.
>>>>>>> login-feature Incoming branch version.

Step 2 - Remove Conflict Markers

git add login.php

git commit

16. Revert

git revert is used to undo the changes introduced by a previous commit without removing that commit from the history.

Instead of changing existing history, Git creates a new commit that reverses the changes of the selected commit.

16.1 What is git revert?

When you use git revert, Git does not delete the old commit. It creates a new commit that applies the opposite changes. 



Before Revert:

A ---- B ---- C

HEAD
 |
 C


After Revert of C:

A ---- B ---- C ---- D

HEAD
 |
 D


D removes the changes made by C.

The original commit C still exists in the history.

Why Do We Need Revert?

In real projects, commits are often already shared with other developers. Removing those commits from history can create problems.

git revert provides a safe way to undo changes while keeping history clear.

Syntax


git revert <commit-hash>

Example


git revert a82f9c4

Git creates a new commit that reverses the changes from commit a82f9c4.

Example Workflow

Suppose the commit history is: 



A ---- B ---- C

C = Added payment feature

Later, the payment feature causes a problem.

Instead of deleting commit C: 


git revert C

Git creates: 



A ---- B ---- C ---- D

D = Revert payment feature

Revert Creates a New Commit

A common misunderstanding is that revert removes a commit.

Actually:

Operation Result
git reset Moves HEAD and can remove commits from visible history.
git revert Creates a new commit that reverses changes.

Reverting Multiple Commits

Multiple commits can be reverted one by one. 


git revert commit1 commit2

Git creates revert commits for those changes.

Revert Without Opening Editor

Normally Git opens a text editor to enter the revert commit message.

To automatically use the default message: 


git revert --no-edit commit_hash

git cherry-pick solves this problem by copying only the selected commit.

With Cherry Pick



feature branch

main branch

A ---- B ---- C


Run:

git cherry-pick D


Result:


A ---- B ---- C ---- D'

Git creates a new commit containing the same changes as D.

18.2 Why Do We Need Cherry Pick?

Cherry-pick is useful when:

  • A bug fix exists in another branch.
  • You need a specific feature without merging everything.
  • You want to move a commit between branches.
  • You need to apply a production fix quickly.

28.1 .gitignore

What is .gitignore?

.gitignore is a file that tells Git which files and folders should not be tracked or uploaded to the repository.

Some files are unnecessary or should remain private, so they are excluded using .gitignore.

Why Do We Need .gitignore?

  • Avoid uploading unnecessary files.
  • Protect sensitive information.
  • Keep repository clean.
  • Reduce repository size.
  • Avoid environment-specific files.

Example .gitignore File



# Python cache files

__pycache__/


# Environment variables

.env


# Node modules

node_modules/


# Log files

*.log

Common Files to Ignore

File/Folder Reason
.env Contains passwords and secrets.
node_modules/ Large dependency folder.
*.log Temporary log files.
build/ Generated output files.
.idea/ IDE configuration files.

Checking Ignored Files


git status --ignored

28.2 Commit Messages

What is a Commit Message?

A commit message describes the changes made in a commit.

Good commit messages make project history easier to understand.

Bad Commit Messages



update

changes

fix

test

These messages do not explain what was changed.

Good Commit Messages



Add user authentication module

Fix payment validation error

Update database connection handling

Remove unused API endpoint

Commit Message Guidelines

  • Use clear descriptions.
  • Keep messages short.
  • Explain what changed.
  • Use present tense.
  • Avoid unnecessary details.

Common Commit Format



<type>: <description>


Example:


feat: add login functionality

fix: resolve database connection issue

docs: update installation guide

Common Commit Types

Type Purpose
feat New feature.
fix Bug fix.
docs Documentation changes.
refactor Code improvement without feature change.
test Adding or updating tests.

Git LFS (Large File Storage)

What is Git LFS?

Git LFS is an extension of Git used to store large files efficiently.

It is not another Git hosting platform and it does not replace GitHub. 



Normal Git:

Repository

 |
 |
Large File


Git LFS:

Repository

 |
 |
Pointer File


Git LFS Storage

 |
 |
Actual Large File

Why Git LFS is Needed?

Git stores file history. Large files create huge repositories.

Example: 



video.mp4

500 MB


Change video


Git stores:

Version 1 = 500 MB

Version 2 = 500 MB


Repository becomes large.

Git LFS stores the large file separately and keeps only a reference inside Git.

Installing Git LFS



git lfs install

Tracking Large Files



git lfs track "*.mp4"

This tells Git to store MP4 files using LFS.

Uploading Using Git LFS



git add .

git commit -m "Add large files"

git push
