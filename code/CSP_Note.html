1. CSP fundamentals

Content Security Policy is a browser-enforced security mechanism. A server sends a policy that tells the browser which sources and execution patterns are allowed for resources such as scripts, styles, images, frames, and network connections.

Core idea: CSP is an additional layer of defense—especially against some cross-site scripting (XSS) attacks. It does not replace output encoding, safe DOM APIs, input validation, authentication, or secure application design.

How it works

Server returns HTML + CSP response header
→
Browser parses policy and enforces it while loading/executing resources

When a resource or operation violates the policy, the browser blocks it (when enforcing) and reports a violation in DevTools. A policy can also be delivered in report-only mode to observe violations without blocking them.

2. Threat model and limits

  • CSP can reduce the impact of injected scripts by restricting script sources and inline execution.
  • A weak policy, overly broad host allowlist, or permissive inline execution can reduce its protection.
  • CSP does not make trusted scripts safe if those scripts contain an injection flaw.
  • Third-party integrations expand the policy surface and should be limited to verified requirements.
Remember: “The page works” is not proof that the policy is strong, and “the console is quiet” is not proof that every intended security control is active.

3. Delivery methods: HTTP header vs meta

HTTP response header (preferred)

Send Content-Security-Policy as an HTTP response header. It can apply to the document before its HTML is parsed and supports the full policy feature set.

Content-Security-Policy: default-src 'self'; object-src 'none'; base-uri 'self';

HTML meta element

<meta http-equiv="Content-Security-Policy"
      content="default-src 'self';">

A meta policy is parsed from the document and has limitations; it cannot provide all header capabilities (for example, reporting directives and some document-level controls). A meta policy also cannot retroactively protect content parsed before it. Avoid treating it as a replacement for a server-managed policy when headers are available.

More-specific directives override their fallback for the resource type they govern. For example, when style-src-elem is present, it governs style elements rather than inheriting the style source list from style-src. A missing directive may fall back to its parent directive, where defined.

Multiple policies: Multiple enforcing CSP headers are not merged as a permissive union. Each policy is enforced, so the combined effect is generally more restrictive. Check for duplicate headers from Apache, a proxy, or application middleware.

5. Style elements vs style attributes

CSP distinguishes stylesheet elements from inline style attributes when the split directives are supported and configured.

<style>
  .notice { color: teal; }
</style>

<div style="color: teal">Hello</div>
  • style-src-elem governs <style> elements and stylesheet links.
  • style-src-attr governs inline style attributes and related style-attribute operations.
  • A nonce on a <style> element does not authorize a separate style="..." attribute.

6. CSP nonces

A nonce is a per-response unpredictable value. The server includes it in the CSP source list and on the specific inline script/style element it intends to authorize.

Content-Security-Policy: style-src-elem 'self' 'nonce-RESPONSE_NONCE';

<style nonce="RESPONSE_NONCE">
  .example { color: teal; }
</style>
Security requirements
  • Generate from a cryptographically secure random source.
  • Use a fresh nonce for each HTML response.
  • Use the exact same value in the header and authorized markup.
  • Do not expose or reuse a fixed nonce across responses.
  • Ensure caching does not pair one response’s HTML with another response’s CSP header.

A nonce is not a general authorization token for all CSS on the page. It applies to supported nonce-bearing elements, not arbitrary attributes or third-party DOM mutations.

7. CSP hashes (SHA-256)

A hash source authorizes inline content only when the browser-calculated digest matches the exact content covered by the relevant CSP rules. Whitespace and content changes can change the digest.

style-src-elem 'sha256-BASE64_DIGEST';

For inline style attributes, CSP requires special handling: in CSP Level 3, a matching hash for an attribute needs 'unsafe-hashes' in the applicable style directive. A hash copied from an error must be applied to the right kind of blocked content and directive.

Why a copied hash may not fix the error: It may describe a different inline block, an attribute rather than a style element, a changed string, or be placed in a directive that does not govern the violation. Do not blindly accumulate hashes from console messages.

Hashes are useful for stable, known inline content. They are usually awkward for dynamic framework-generated or third-party CSS that changes across versions or runtime states.

8. What 'unsafe-inline' means

'unsafe-inline' relaxes CSP’s restrictions on inline code for the directive where it is used. In a style directive, it permits inline styling more broadly; it is not the same as allowing a single nonce-authorized style block.

Policy choiceEffectTrade-off
Nonce on style elementsAllows only matching nonce-bearing style elementsRequires correct server-side nonce plumbing
Hashes for stable blocksAllows exact matching inline contentFragile if content changes; attributes need special handling
style-src-attr 'unsafe-inline'Allows inline style attributesBroadly relaxes attribute-style restrictions
style-src 'unsafe-inline'Broad inline-style allowance in the style policyLess granular; review carefully

Using style-src-attr 'unsafe-inline' can be a compatibility decision, but it should be explicit, tested, documented, and approved. It is not automatically “safe” just because it is narrower than putting 'unsafe-inline' in style-src.

9. Angular and CSP

Angular may create style elements for component styles at runtime. Angular’s ngCspNonce attribute supplies a nonce to Angular’s style creation mechanism in supported versions/configurations.

<app-root ngCspNonce="SERVER_GENERATED_NONCE"></app-root>

The value must be present in the delivered HTML and match the nonce in the CSP header. A static placeholder does nothing unless a server-side mechanism replaces it correctly.

Important distinction: Angular’s nonce helps authorize Angular-created style elements. It does not automatically add a nonce to styles inserted by every third-party script, nor does it authorize ordinary style attributes.

10. Angular ngStyle and ngClass

[ngStyle]

ngStyle applies style properties to an element at runtime. It can appear to work even while CSP blocks or restricts some style operations, depending on the browser, exact operation, policy, and whether a violation occurs. Working visually does not prove that CSP authorizes it under every supported browser or policy.

<p [ngStyle]="{'margin-top.px': 10}">Consent text</p>

For fixed presentation, prefer a CSS class where practical:

<p class="consent-text">Consent text</p>

/* component stylesheet */
.consent-text { margin-top: 10px; }

[ngClass]

ngClass toggles class names; the corresponding CSS rules live in stylesheets. It is generally a good way to express state-based presentation without setting a style attribute directly.

<button [ngClass]="{'is-disabled': isDisabled}">Continue</button>

/* CSS */
.is-disabled { opacity: .55; }

However, ngClass is not a CSP bypass: the stylesheet containing the class must still be allowed, and the class name must not be used to inject untrusted CSS or HTML.

11. Apache response headers

Apache’s mod_headers can set response headers. Keep the policy in one authoritative place where possible, and confirm whether a reverse proxy or application layer also emits CSP.

Header always set Content-Security-Policy "default-src 'self'; object-src 'none'; base-uri 'self';"

In Apache configuration, quoting and expression syntax depend on the directive and Apache version. Do not assume a string such as %{SOME_VAR}e is automatically evaluated in every context; header interpolation has specific syntax and environment-variable requirements.

Do not paste illustrative snippets directly into production. Preserve existing required directives, validate Apache syntax with its configuration test command, and test in a non-production environment first.

12. Apache UNIQUE_ID and the @ issue

mod_unique_id supplies a request identifier. It is useful for correlation and logging, but it is not intended to be a cryptographically secure CSP nonce generator.

Your earlier implementation used %{UNIQUE_ID}e and encountered an @ character in the generated value. Replacing characters can make a string syntactically convenient, but it does not upgrade the source into a secure nonce generator.

Key takeaway: Do not rely on UNIQUE_ID plus character substitution as the final secure nonce design. Prefer a cryptographically secure random generator and coordinate the header and HTML values.

13. SSI and mod_substitute

SSI

Server Side Includes can insert server-side values into HTML when the response is configured for SSI processing. SSI does not itself generate secure randomness, and it does not automatically share arbitrary variables with a Lua handler.

mod_substitute

mod_substitute performs response-body substitutions. It is not a secure nonce generator, and broad regular-expression rewriting of large HTML responses can add processing cost or interact unexpectedly with other output filters.

Your investigation also encountered literal/unexpanded environment placeholders and concerns about combining substitution with SSI. Treat output-filter ordering and variable expansion as implementation-specific; verify the actual response bytes and headers rather than assuming a directive expands as intended.

14. Apache Lua: what it can and cannot solve by itself

mod_lua allows Apache to run Lua handlers and filters when the module is built and configured compatibly. Installing the Lua interpreter alone does not install or enable Apache’s mod_lua.

  • Lua 5.1.4 being available on the server does not prove that Apache has a compatible Lua module.
  • A Lua script file sitting on disk is not invoked unless Apache configuration connects it to an appropriate hook or handler.
  • math.random() is not suitable for generating CSP nonces.
  • The chosen implementation must securely generate a nonce and make the same request-scoped value available to both header and HTML.
Architecture caution: A Lua fixup hook that sets an environment variable is not, by itself, a complete HTML-rewriting solution. Apache’s header processing and response-body processing are separate concerns. A working design needs a verified supported mechanism for both, and must account for caching, compression, and filter order.

Before implementing: verify Apache version/build, whether dynamic modules are supported, whether a compatible mod_lua exists, and the documented APIs available in that exact build. Test only in development/staging first.

15. Razorpay checkout and inline styling

Your observed checkout behavior included a dynamically inserted style block (for example, a spinner animation) and elements carrying inline style attributes. These are different CSP cases.

  • A stylesheet host source such as https://*.razorpay.com permits eligible external resources from that origin pattern; it does not authorize arbitrary inline style attributes.
  • A nonce on Angular’s root element does not automatically nonce Razorpay-created style elements.
  • A nonce on a style element does not authorize Razorpay’s separate style attributes.
  • A SHA-256 hash only addresses exact matching content in the applicable context; one hash should not be assumed to authorize unrelated styles.

Use Razorpay’s current official integration and security documentation to verify required script, frame, connection, image, and form destinations for the exact checkout integration you use. Avoid inventing or broadly allowing domains. Do not edit vendor checkout.js as a workaround.

Practical decision: If the checkout requires inline style attributes and there is no supported way to avoid them, a narrowly scoped style-src-attr 'unsafe-inline' may be a compatibility option after security review. It is not proof that no other integration option exists.

16. Errors and issues encountered — case notes

Case 1 — Inline style blocked

Symptom: Browser reports that inline styling violates style-src.

Diagnosis: Identify whether the violation is a style element, a style attribute, or a dynamic CSS operation. Read the exact directive named in the error.

Resolution path: Apply a nonce/hash only when it matches the relevant content and directive; otherwise refactor to classes or adjust policy deliberately.

Case 2 — Angular style elements lacked a nonce

Symptom: Angular-generated styles are rejected under a nonce policy.

Diagnosis: Check the delivered root element’s ngCspNonce and inspect generated style elements’ nonce properties.

Resolution path: Ensure the server injects a per-response nonce and the CSP header carries the identical value.

Case 3 — Apache UNIQUE_ID contained @

Symptom: Nonce string caused formatting/validation issues.

Diagnosis: Request IDs are not designed as secure CSP nonce values.

Resolution path: Replace the design with cryptographically secure randomness rather than depending on character substitution.

Case 4 — Placeholder was not expanded as expected

Symptom: HTML/header contained a literal variable placeholder.

Diagnosis: Apache directives do not all expand environment variables the same way; substitution replacement syntax and filter timing matter.

Resolution path: Verify actual HTTP response headers and body; use a supported request-scoped mechanism.

Case 5 — SSI and substitution complexity

Symptom: Multiple output filters and regex replacement made behavior harder to reason about and raised performance concerns.

Diagnosis: Body filters can interact; repeated rewriting of HTML is not a nonce-generation strategy.

Resolution path: Minimize transformations and test exact output, response time, compression, and caching.

Case 6 — PHP entry-point returned “File not found”

Symptom: Testing an index.php wrapper produced a 404-style response although a file appeared to exist.

Diagnosis: Potential causes include PHP-FPM path/chroot configuration, incorrect SCRIPT_FILENAME, permissions, or Angular rewrite rules intercepting the request. The precise cause must be confirmed from logs/config.

Resolution path: Check Apache error logs, FastCGI parameters, filesystem mapping, and rewrite order. Do not assume one cause without evidence.

Case 7 — SHA-256 hash added but violation continued

Symptom: Adding a hash did not clear the CSP error.

Diagnosis: Confirm the exact blocked content, directive, digest, and whether the violation concerns an attribute. Hashes are content-specific.

Resolution path: Use the exact browser error, inspect the affected element, and avoid copying a hash from one violation to another.

Case 8 — One hash appeared to clear multiple errors

Symptom: A single hash seemed to remove several visible style errors.

Diagnosis: This observation alone does not prove the hash authorized all style blocks. Browser logging, stylesheet reuse, and changed execution paths can affect what appears in the console.

Resolution path: Verify each relevant element and behavior independently. Do not infer a general CSP rule from a quiet console.

Case 9 — Razorpay injected CSS

Symptom: Checkout added a style block and inline style attributes.

Diagnosis: Separate style-element violations from style-attribute violations. Angular’s nonce does not automatically cover Razorpay’s DOM changes.

Resolution path: Check current provider requirements, use exact applicable hashes/nonces where feasible, or document and approve a narrowly scoped compatibility exception.

Case 10 — ngStyle vs CSP

Symptom: Angular ngStyle appeared to work despite concerns.

Diagnosis: Runtime appearance is not a complete CSP compliance test; behavior depends on the precise style operation and browser.

Resolution path: Prefer CSS classes for static styling and test dynamic styling under the actual enforced policy.

17. Browser debugging workflow

  1. Open DevTools → Network → select the document request → inspect all response headers.
  2. Find every Content-Security-Policy header and any CSP meta element.
  3. In Console, copy the complete violation, especially the directive name and suggested hash/nonce text.
  4. Inspect the affected element and determine whether it is a <style>, linked stylesheet, style attribute, or script-driven style operation.
  5. Check Angular’s root ngCspNonce and compare it to the CSP nonce exactly.
  6. Test the same interaction in a clean session and after a hard reload; account for cache and service-worker behavior.
  7. Use report-only mode in a controlled test when evaluating a proposed policy, then test enforcement.
// Inspect inline style-bearing elements around Razorpay checkout:
[...document.querySelectorAll(
  '.razorpay-container [style], .razorpay-container style'
)].map(el => ({
  tag: el.tagName,
  style: el.getAttribute('style'),
  text: el.tagName === 'STYLE' ? el.textContent : null,
  nonce: el.nonce || ''
}));

This is a diagnostic snippet; run it in DevTools after the checkout DOM exists. It does not modify the page.

18. Why development may differ from UAT/production

  • Development servers may use different headers, proxies, build modes, or relaxed policies.
  • UAT/production may serve static files directly, use PHP-FPM, add proxy headers, or apply different rewrite rules.
  • Cached HTML can mismatch a newly generated CSP nonce if caching is not designed for nonce-bearing documents.
  • Build optimization, lazy-loaded modules, third-party scripts, and different checkout paths may reveal additional violations.
  • Permissions, filesystem paths, and custom Apache builds can differ across environments.

Compare the actual response—not only the configuration file—between environments.

19. Policy design example (illustrative only)

The following demonstrates directive structure, not a ready-to-deploy policy. Replace sources with verified requirements, insert a real server-generated nonce, and retain any necessary application directives.

Content-Security-Policy:
  default-src 'self';
  base-uri 'self';
  object-src 'none';
  frame-ancestors 'self';
  script-src 'self' https://checkout.razorpay.com;
  style-src-elem 'self' 'nonce-RESPONSE_NONCE' https://*.razorpay.com;
  style-src-attr 'unsafe-inline';
  img-src 'self' data: https://*.razorpay.com;
  connect-src 'self' https://api.razorpay.com;
  frame-src 'self' https://api.razorpay.com https://checkout.razorpay.com;
  form-action 'self';
Do not copy this blindly: The Razorpay origins shown are examples based on the troubleshooting context, not a complete verified provider allowlist. Confirm current official requirements. Also review whether script nonces, strict-dynamic, report-uri/report-to, worker-src, font-src, media-src, and other directives are needed for your application.

20. Final implementation checklist

  • □ Inventory all CSP headers and meta policies across app, proxy, and Apache.
  • □ Start with report-only testing where feasible; review violations.
  • □ Generate nonce with a cryptographically secure source, once per HTML response.
  • □ Confirm identical nonce in CSP header and Angular’s delivered ngCspNonce.
  • □ Ensure HTML caching cannot mismatch the nonce/header pair.
  • □ Distinguish style-src-elem from style-src-attr.
  • □ Prefer CSS classes for static styling; review dynamic ngStyle uses individually.
  • □ Treat Razorpay’s injected styles separately from Angular’s generated styles.
  • □ Verify hashes against exact content and the correct directive.
  • □ Avoid using UNIQUE_ID or math.random() as CSP nonce sources.
  • □ Avoid broad response-body regex rewriting unless thoroughly justified and tested.
  • □ Verify Apache module/build compatibility before enabling Lua.
  • □ Test login, logout, modals, checkout open/close, success/failure flows, lazy routes, and refresh.
  • □ Validate Apache configuration before reload; follow change approval and rollback procedures.
  • □ Document any 'unsafe-inline' exception, its scope, rationale, and approval.
